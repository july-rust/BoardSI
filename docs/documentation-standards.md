## 2. 반드시 구분하는 상태 용어

| 상태 | 의미 | 사용 예 |
| :--- | :--- | :--- |
| **PASS — scoped** | 명시한 샘플·플랫폼·테스트 **범위에서** 성공 | 공개 합성 PADS V9.4의 Via 접촉 후보 |
| **PARTIAL** | 일부 기능·입력 형상만 구현/검증 | PADS Import, Artwork, Reference Preview |
| **NOT_RUN** | 지정된 시험 자체를 실행하지 않음 | 공식 Txx 제품 수락시험 |
| **NOT_VERIFIED** | 실행 여부/결과를 떠나 **충분한 정식 근거 없음** | 실제 제조 PCB SI 오차 보증 |
| **BLOCKED** | 다음 단계로 승격하기 위한 필수 조건 미충족 | M0 formal exit gate |
| **FAIL** | 수행된 검사에서 요구 기준 위반 확인 | 원본 PH-08 HMM Gate Q |
| **PROPOSED / NOT_FROZEN** | 검증 기준이나 계약이 확정되지 않음 | 일부 PH-08 제안 계약 |
| **CLOSED (administrative)** | Issue·PR 관리 상태 | 물리 오류가 해결됐다는 뜻이 아님 |

`PASS`는 반드시 **무엇이 통과했는지** 주어가 있어야 합니다. `17 required status contexts green`은 저장소 보호 규칙의 결과이지, U/T 54건 정식 인수가 아닙니다. GitHub PR이 Merged여도 별도 main Push 워크플로가 자동으로 PASS로 증명되는 것은 아닙니다.

## 3. 증거 기록의 필수 요소

새 검증 결론에는 가능하면 다음을 한 번에 기록합니다.

1. **객체:** Stage/Requirement Uxx/Test Txx, 코드 경로, 플랫폼 및 관련 Issue·PR 번호.
2. **시점:** **최초 체크일**과 **증거일**(`YYYY-MM-DD KST`). 다른 날짜인 경우 둘 다 기록.
3. **출처:** 실제 실행 SHA, PR-head/run URL, 재현 가능한 공개 픽스처 경로 및 입력 원본 해시.
4. **검증 계약:** 모델·정밀도·단위, Pass/Fail 경계, 독립 오라클·참조를 사용할 경우 그 출처.
5. **관측 결과:** 실제 통과/실패 개수, 오류 메시지와 실패 사례, 미지원 형상/플랫폼.
6. **독립성:** 구현 테스트, 독립 계산/원본 검증, GUI 리그레션, 실물 물리 검증을 혼동하지 않음.
7. **잔여 제약:** 정식 U/T, 전역 Connectivity, 실측 보드/배포 등 미완을 명시.

문서에서 확인된 사실은 링크/커밋으로 뒷받침하고, 추론/제안은 `제안`, `추정`, `미확인` 등으로 표시합니다. 수치/단위는 **SI 단위(mm, m, Hz, Ω, H/m, F/m 등)**를 기본으로 쓰되, 입력 포맷의 `MILS`와 SOURCE Tick은 **외부 파일 형식 식별자**이므로 삭제하거나 임의로 치환하지 않습니다. PADS V9.4 MILS의 제한 SOURCE Grid는 1 Tick = 0.000254 mm입니다.

## 4. 가독성과 구조

- 첫 두 문단에 **문서 목적·적용 범위·검증 경계·증거 기준일**을 명시합니다.
- 제목은 하나의 H1 아래 H2/H3 순서로 작성합니다. 표는 항목 성격/비교에만 사용하며, 긴 원시 로그나 셀 전체의 소스 SHA를 메인 표에 쌓지 않습니다.
- 메뉴와 표의 한 항목은 **하나의 목적**만 설명합니다. 중복 상태표를 계속 복제하는 대신 단일 원장으로 링크합니다.
- 문서의 상대경로 링크는 실제 Git 저장소에서 존재하는 파일을 가리켜야 합니다. 디렉터리 링크는 `README.md`로 명시적으로 연결하는 편을 권장합니다.
- 오래된 결정문은 **당시의 근거**로 보존하고, 현재와 다른 결론은 본문 맨 위에 `Historical checkpoint — superseded by ...` 형태의 주석과 링크를 둡니다.
- 과거 수치 오차·Fail 사례는 불편하더라도 삭제하지 않습니다. 오류 정정은 `Erratum: <날짜> — 기존 문장의 무엇을 고쳤는지`를 기록해 추적합니다.
- `README.md`는 3분 내 전체 구조 파악이 가능하도록 유지하고, 실무 상세 절차는 [Getting started](getting-started.md)로 분리합니다.

## 5. 변경·리뷰·CI 운영

1. **코드 변경**: 같은 PR에서 해당 기능의 제한 범위와 시험 증거를 업데이트하는 것이 원칙. 요구사항 공식 완료 전에는 Txx를 PASS로 표시하지 않습니다.
2. **문서 정정**: 순수 Markdown 수정은 작은 수의 의미상 관련 문서만 한 PR로 묶습니다. 오래된 이슈의 과거 증거 문서를 일괄 재작성하지 않습니다.
3. **문서 변경 감지**: 순수 `docs/**/*.md` 변경은 분류기가 올바르게 인식하는 경우 불필요한 네이티브 작업을 SKIP할 수 있습니다. 그러나 **현재 전체 Markdown 경로에 일관되게 적용되지는 않습니다**. 컴포넌트 README와 일부 F6/F7 작업의 기존 누락은 [Issue #513](https://github.com/july-rust/BoardSI/issues/513)에서 추적합니다. 필수 체크는 그대로 유지하고 실제 PR-head `docs` 검사, 분류기, 각 네이티브 작업의 SKIP/PASS를 확인해야 합니다.
4. **경로·구조 검증**: 로컬 Markdown 링크의 대상 파일 존재 여부, `#anchor` 안정성, 이미지 경로, 중복 제목, 존재하지 않는 섹션 이동, 금지된 기업 정보 노출을 점검합니다. 상대 파일 링크가 있다고 해서 외부 URL의 최신성이나 내부 앵커의 유효성이 자동 보장되는 것은 아닙니다.
5. **병합**: 보호된 `main`, Verified·Squash-only·필수 CI·리뷰 정책을 준수하고, 병합 SHA와 필요한 main Push 결과를 별도로 구분합니다.
6. **범위 이동**: 새로운 Via/Pad 접촉 형태를 **각도별 케이스로 재구현하지 말고**, 기존 공통 기하 엔진 또는 일반화된 도체 Footprint API를 확장한 뒤 모델 불변성·대칭성·경계조건 시험으로 검증합니다.

## 6. 외부 리뷰 체크리스트

- 처음 보는 사람이 3번 이하의 클릭으로 **사양서 / 현재 상태 / 실행 방법 / 실제 검증 보고서**에 도달할 수 있는가?
- `구현됨`과 `정식 검증됨`이 구별되는가?
- 오래된 Issue/PR이 여전히 OPEN으로 표시되지는 않는가?
- 각 PASS에는 **시험 환경·입력·결과·코드 SHA**가 있는가?
- Stage A/B/C/D의 한정 체크가 U/T 제품 인수와 분리되는가?
- PH-08 실패, 미지원 객체, 자료 보안과 미선정 라이선스가 은폐되지 않았는가?
- 이 변경이 코드/CI 설정을 바꾸지 않았는데 불필요한 네이티브 검증을 다시 실행하지는 않는가?
